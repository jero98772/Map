1 · Overview: the pipeline

~10 min · ★☆☆

Language spotlight: Java

python_interpreter_java/Main.java: the same pipeline with records, a sealed Node interface and pattern-matching switch.

An interpreter is a program that reads another program and runs it. MAP ("Make A Python") is a tiny subset of Python, with integers, booleans, None, variables, + - < <= ==, if/else, def/return, recursion, for … in range(…), and the builtins print and range. Small as it is, it already needs every stage of a real interpreter.

  1. Source: the program as one string.
  2. Tokenizer: turns characters into words like DEF, NAME fib_rec or INDENT.
  3. Parser: checks the words against the grammar and builds a tree.
  4. AST: the tree of node objects (FuncDef, If, BinOp …).
  5. Semantic analysis: decides which names are local or global, and rejects programs that are wrong without running them.
  6. Tree-walk evaluation + memory: visits the tree, creating frames and values.
  7. Output: what print writes.

Real CPython takes a side road after the AST: it compiles the tree to bytecode and runs that on a virtual machine. MAP never makes bytecode; it walks the tree directly.

2 · Reading: turning characters into words

Tokenizer

~30 min · ★★☆

Language spotlight: Java

List<Integer> stack; record Token(TT type, Object value, int line, int col).

Think of reading a sentence. Before you can understand it, you split it into words. The tokenizer does exactly that for your program.

The tokenizer (also called lexer or scanner) reads the source one character at a time and groups characters into tokens. The method is a hand-written scanner: a loop that asks for the next token until the end of the text. Each call looks at the current character and decides what kind of token starts there.

A token remembers its type, its value and where it came from (line and column). Error messages need that position later.

INDENT and DEDENT

Think of nested boxes: every box you open, you must close. INDENT opens a box, DEDENT closes one.

Python has no braces, so blocks come from leading whitespace. At the start of every line the lexer counts the spaces and compares the count with the top of a stack, indent_stack, which starts as [0]:

  • more spaces than the top: push the new width and emit INDENT
  • fewer spaces: pop and emit one DEDENT per popped level
  • after popping, the width must equal the new top, otherwise IndentationError
  • blank lines and comment-only lines are skipped and never touch the stack.

At the end of the file, every level still open gets a DEDENT. That is why INDENT and DEDENT always balance.

3 · Grammar: do the words form a sentence?

Parser (syntax analysis, PEG)

~45 min · ★★★

Language spotlight: Java

Each rule returns a record such as Compare; expect throws ParseError.

Think of a grammar teacher diagramming a sentence: subject here, verb there. The parser does the same with your tokens. It checks that they fit the grammar and draws the structure.

The parser checks that the tokens form a valid program and builds the tree. MAP's grammar written as a PEG (Parsing Expression Grammar):

How to read it: e1 e2 is a sequence, e* is "zero or more" (a while loop), e? is optional, and e1 / e2 is an ordered choice. The parser tries e1 first and only tries e2 if e1 fails. There is never any ambiguity, because the first alternative that succeeds wins.

Optional deep dive: Backtracking

You can skip this part. None of the six interpreters backtracks, but it explains what "PEG" means.

When an alternative fails halfway, the parser must rewind. Before trying an alternative it saves the cursor position, and on failure it restores it:

Example: on print(fib_rec(4)), assign matches NAME print, then needs '=' but finds '('. It fails, the cursor goes back to 0, and expr_stmt parses the whole line.

Packrat memoization

Backtracking can make the parser repeat work, for example in comparison <- sum '<=' sum / sum. Both alternatives start by parsing sum at the same position. A packrat parser keeps a memo table (rule, position) → (node, end position), so each rule runs at most once per position and parsing stays linear:

History corner · Before PEG: CPython's LL(1) parser

Picture Python 3.8. You type f() = 1. The parser looks at it and says: fine! Only a later stage notices the problem and complains: "can't assign to function call". Why did the parser let it through? Because of how it was built.

For almost 30 years CPython did not use a PEG. Until Python 3.8 its parser was generated by pgen from the file Grammar/Grammar, and it was an LL(1) parser:

  • L: it reads the tokens from Left to right;
  • L: it builds the Leftmost derivation (it always expands the leftmost rule first, top-down);
  • (1): it decides with exactly 1 token of lookahead.

An LL(1) parser is table-driven and never backtracks. It keeps a stack of rules still to match, and a table maps (rule on top of the stack, next token) to exactly one production. If the cell is empty, the program is a SyntaxError.

That power has limits. The grammar cannot be left-recursive, and every choice must be decidable from one token. So some rules were written too loosely and repaired later: f() = 1 parsed as a valid statement and was only rejected while building the AST ("can't assign to function call"). Parenthesised with statements and match could not be expressed at all. PEP 617 replaced it with the PEG parser in Python 3.9 (the old one was still available with -X oldparser), and the LL(1) parser was removed in 3.10.

MAP's parser sits close to the old one: it is hand-written recursive descent that decides with one token, or two at NAME '=' (LL(2)). That is why it never needs the PEG backtracking explained above.

What the interpreters actually do

All six interpreters call their parser "PEG-style", but they never need to rewind. Each ordered choice is decided by peeking one or two tokens ahead. That works because MAP's alternatives start with different tokens (def, if, for), or can be told apart by the second token (NAME '='). The result is the same tree, built without backtracking or memoization.

Each grammar rule is one function that returns an AST node. Precedence comes from which rule calls which: comparison calls sum, so + binds tighter than <=.

4 · The skeleton: your program as a tree

AST and tree walk

~20 min · ★★☆

Language spotlight: Java

sealed interface Node + records; a pattern-matching switch must handle every case.

Take a sentence and remove the punctuation. What is left is the skeleton: who does what to whom. The AST is the skeleton of your program.

The Abstract Syntax Tree keeps only what matters for running the program. There are no parentheses, colons or indentation; those exist only to shape the tree. Every node is a small class:

Composite pattern. A node can contain other nodes (a FuncDef has a body, a BinOp has left/right), and code treats a single node and a whole subtree the same way. Name and the literals are the leaves.

Before you scroll: sketch the tree for fib_rec(n - 1) + fib_rec(n - 2).

A BinOp '+' with two children. Each child is a Call to Name('fib_rec') whose argument is a BinOp '-' of Name('n') and an IntLiteral. Find it in the tree for A below.

Walking the tree: Visitor

To do something with every node (print it, check it, run it) you need code per node type. The Visitor pattern keeps that code out of the node classes: a visitor has one function per node type, and a dispatcher picks the right one:

A node's handler visits its children by calling the dispatcher again, which gives a depth-first walk. The evaluator itself is the Interpreter pattern: each grammar construct has a class, and evaluating the tree means asking each node to evaluate itself.

5 · Meaning: what does each name refer to?

Semantic analysis

~15 min · ★★☆

Language spotlight: Java

No semantic pass; a top-level return is turned into a SyntaxError at runtime by Interpreter.run. Java's twist: None is null, so lookup needs containsKey instead of get.

What does this print?
x = 1
def f():
    print(x)
    x = 2

f()

Most people guess 1. CPython raises UnboundLocalError, and MAP prints 1. This chapter explains why.

Think of an environment as a sticky note. It lists some names and their values, and points to the note behind it. To find a name, you read your note first, then the one behind, and so on.

A program can be grammatically correct and still be wrong. Semantic analysis is a pass over the AST, after parsing and before running, that works out what names mean and rejects what can be rejected early.

Scope resolution: local or global?

Python's rule: a name that is assigned anywhere in a function body is local to the whole function. Parameters are local too. Any other name is looked up in the global scope, then in the builtins. For Program B:

  • 'return' outside function and duplicate argument are caught by CPython's compiler before any code runs. None of the six interpreters has a full semantic pass. MAP runs the first program anyway: the return signal escapes to the top and is reported as an InternalError. It silently accepts the duplicate parameter.
  • UnboundLocalError: CPython decided at compile time that x is local in f (it is assigned on line 4), so reading it on line 3 fails. MAP has no such pass. Its environment lookup walks up to the global x and prints 1, which is a known difference.
  • NameError cannot be detected early. In the last program, f mentions g before g exists. By the time f() runs, g has been defined. Whether a global name exists depends on what has executed so far (definitions can be conditional), so the check must happen during the lookup itself.

6 · Bringing it to life: frames, calls, return

Evaluation and memory

~30 min · ★★★

Language spotlight: Java

ReturnSignal is a RuntimeException without a stack trace, so it is cheap.

Two images help here. The call stack is a stack of plates: each call puts a plate on top, and each return takes it off. A return is an emergency exit: it skips every room between you and the door.

The evaluator walks the AST and does what each node says. While it runs, memory has two parts, the same ones Python Tutor draws:

  • Frames (left in the videos): one Environment per active call, mapping names to values. The global frame is created first.
  • Objects (right): values that variables refer to, such as function objects. Small ints are shown inline.

Calling a function

  1. Evaluate the callee and the arguments.
  2. Create a new Environment whose parent is the function's closure (the global frame for MAP's top-level functions).
  3. Bind each parameter to its argument.
  4. Execute the body. return sends a return signal with the value, which unwinds out of nested if/for blocks to the call.
  5. Catch it, discard the frame, and hand the value back.
Guess first: how deep will the stack get for fib_rec(4)? Then watch the videos below.

The call stack is the chain of active frames. In MAP it is not a separate data structure: every call is a call in the host language, so the host's own stack holds it. Program A reaches a depth of 4 frames (fib_rec(4) down to fib_rec(1), plus global).

The videos show one step per executed line, recorded by an Interpreter subclass in capture.py that only watches; the evaluation is main.py's own. Program A takes 39 steps and Program B takes 25. Just before fib_iter(6) returns, its frame is {"n": "6", "a": "5", "b": "8", "i": "6", "temp": "8"} and the return value is 8.

In the videos, watch the stack grow, then collapse back to 3.

PyError extends RuntimeException plus subclasses. Why does Java raise RecursionError while Rust crashes? The JVM throws StackOverflowError, and the interpreter catches it.

How an error is reported. A runtime error raised deep inside a recursion passes through every call (none of them catches it) until main() catches it and prints Kind: message [line N]:

Line and column. Every token stores line and col, but the error reports only the line, and the column is lost. Reporting columns means passing the token's column into the error and printing the source line with a ^ under it, as CPython does:

RecursionError. MAP does not count calls. A runaway recursion exhausts the host Python's stack, and main() reports that as InternalError. Java catches StackOverflowError, the llvm port counts calls up to MAX_DEPTH = 4000, and Rust, C++ and Clojure simply crash. A faithful version keeps a depth counter in the call and raises at 1000, as CPython does.

8 · Crossing the border: print and range

Builtins

~15 min · ★☆☆

Language spotlight: Java

reg(name, lambda) into a LinkedHashMap; this range checks for step 0.

Think of power outlets. Your MAP program plugs into them, and the electricity comes from the host language.

A builtin is a function written in the host language rather than in MAP. MAP needs two of them, print and range. Each interpreter defines 14 and registers all of them the same way: as ordinary values in the global Environment.

When a Call node runs, the callee is looked up like any variable. If the value is a host callable rather than a MAP function, it is called directly with the list of evaluated arguments. That is the point where MAP code crosses into native code. Python Tutor hides builtins in its frames, and so do the videos.

9 · Bonus: real CPython bytecode

~15 min · ★★☆

Language spotlight: Java

A tree-walker: if and for are Java statements inside the pattern switch.

CPython does not walk the tree. It compiles each function into bytecode, a flat list of instructions for a stack machine, and control flow becomes jumps. Below is dis.dis for both functions, run with Python 3.14. Bytecode is an implementation detail: it differs between Python versions, so on 3.12 or 3.13 you will see other instruction names.

  • if n <= 1: becomes COMPARE_OP followed by POP_JUMP_IF_FALSE … (to L1), which skips the return n when the test is false.
  • for becomes GET_ITER, then FOR_ITER (to L3) at the top of the loop (it leaves when the iterator is exhausted) and JUMP_BACKWARD (to L2) at the bottom.

Tree-walkers use no jumps

A tree-walker never needs jumps: an If node is executed by a host if, and a For node by a host for. The structure of the tree is the control flow. Only a compiler needs jumps — like CPython, and like the LLVM port.

10 · Expansion packs

Out of scope

Think of what follows as expansion packs, ready for you to build.

This tutorial covers the language core only. MAP has no standard library, no import or modules, no classes or objects, and no operating-system APIs (files, sockets, processes, environment). It also leaves out while, try/except, strings, lists, floats and / // %. Most of these exist in the six full ports and are left out of MAP on purpose. Each one is a new token, a new grammar rule, a new node, and a new evaluation function, built with exactly the same steps as above.

11 · Your turn: build your own Python

You have seen every piece. Now build it yourself. Pick a host language: one of the six, or one that is not here yet (Go, C#, Haskell, JavaScript, Zig …). Then go through the tutorial in order, one stage at a time:

  1. Tokenizer: a scanner loop and an indent stack that emits INDENT and DEDENT.
  2. Parser: one recursive-descent function per grammar rule, deciding with one or two tokens of lookahead.
  3. AST: one node type per construct, and a dispatcher that picks the handler for each node.
  4. Environments: {vars, parent}, with lookup walking up the parent chain.
  5. Calls and return: a new environment per call, and a return signal that unwinds to the call.
  6. Errors: one class per stage, each carrying a line number, reported in one place.
  7. Builtins: print and range as host functions stored in the global environment.

Final check

  • Program A prints 3 and Program B prints 8.
  • The programs in tutorial/examples/errors/ fail with the messages from chapters 3 and 7.

Each one is a new token, a grammar rule, a node and an evaluation function — exactly the steps you already know.
